# Methodology

How every number in this repository is produced and reported. A result that does not follow these rules is not published.

## What is being tested

**DQL's Ask AI answering business questions in plain English over a dbt project.** Every benchmark is set up the way a DQL customer works: a dbt project builds the warehouse, DQL is initialised on that project, and each benchmark question is asked through Ask exactly as a user would ask it. Ask's answer — the rows it returns — is compared with the benchmark's correct answer.

Where a benchmark already ships a dbt project, that project is used as published. Where it ships only a database, a dbt project is generated by a script, identically for every database: the tables become dbt sources, each gets one staging model that leaves the data unchanged, and the benchmark's own column descriptions become the model documentation. Nothing in that generation looks at the questions.

## The scorecard

DuckCode sells DQL on these numbers, so a result is published only with every row of this scorecard filled in, or marked "not measured" with the reason. A buyer asks all of these questions, not just "how accurate".

| Angle | What we report | How |
|---|---|---|
| Accuracy | right answers per layer, paired between layers | row matching (§7), Wilson CI, McNemar (§1) |
| Accuracy that holds up | accuracy on the audited subset; answers that match only by chance on small data, flagged | answer-key audit (§4); a second check of which tables each answer used |
| Trust | right/wrong × `certified` / `governed` / `review_required`; **wrong-but-certified, target 0** | run receipts (§5) |
| Knowing when to stop | questions the data cannot answer: refused or clarified vs answered anyway | a separate unanswerable set, written from the schema, never scored as part of accuracy |
| Speed | median and 95th-percentile seconds per question; AI calls per question | run receipts (§6) |
| Cost | dollars per question at list price, per provider | provider token counts (§6); "not measured" on subscription routes |
| Stability | same answer across repeated runs; same answer for reworded questions | repeats per layer; a reworded-question set written without the answers |
| Data safety | result rows sent to the AI model (target 0 in Ask); what the model saw | provider egress receipts |
| Setup effort | hours to write each layer, and by whom | timed authoring log per layer |
| Model choice | the same table for each provider: subscription CLI, Anthropic API, other model families, a local model | one run set per provider |
| Reproducibility | replaying the recordings reproduces the accuracy columns exactly | replay on a clean checkout (§9) |
| Defects found | DQL defects the benchmark uncovered, the fix, and the release that carries it | the benchmark's REPORT.md |

A defect the benchmark uncovers is fixed in DQL as a general fix (never a rule about a benchmark question), described in the report, and scored on a released version that contains it.

## 1. Paired comparisons only

A claim always compares two **conditions** on **the same questions** scored by **the same grader**:

- per condition: correct / total, accuracy, and a **Wilson 95% confidence interval**;
- between conditions: the questions only one of them got right, an **exact two-sided McNemar test**, and the difference in accuracy with a 95% interval.

A single accuracy figure on its own is never published. The scorer is `paired/paired-compare.mjs`; it refuses reports that answer different questions.

## 2. The conditions: DQL's layers on one dbt project

Each condition is a copy of the same dbt project with one more DQL layer switched on:

| Step | What the project has | What it tells a customer |
|---|---|---|
| **L0** | the dbt project only; DQL reads its models and documentation, and Ask writes SQL over them | what DQL gives on day one |
| **L1** | + DQL modeling: a domain, entities, relationships and certified joins | what describing how the tables connect is worth |
| **L2** | + the dbt semantic layer (MetricFlow), where the project has one | what governed metric definitions are worth |
| **L3** | + DQL skills: business definitions and rules | what written business vocabulary is worth |

Each step adds exactly one layer, so each row of the results table shows what that layer is worth on its own. The time spent authoring each layer is recorded and published beside the gain it produced.

## 3. Provenance

- Runs are recorded once against a real AI provider and replayed from those recordings. Only recordings from a real provider count; test fixtures and synthetic recordings are refused by the scorer.
- Every report carries an identity block: this repository's commit and whether it had uncommitted changes, the DQL version, whether it came from an npm release (or, for a development build, its commit), the provider and model, the recording mode, a fingerprint of the adapter code, and a hash of the downloaded data.
- Only runs of a **released** DQL version, from a **clean** checkout, with **recorded** AI calls are publishable.
- Because a small question set has wide error bars, each condition is run several times. Reports show the accuracy of each run and how often the same question got the same answer.

## 4. The answer key is audited

Public answer keys contain mistakes. A 2026 audit ([arXiv 2601.08778](https://arxiv.org/abs/2601.08778)) found 52.8% of BIRD mini-dev and 62.8% of Spider 2.0-Snow gold annotations wrong, enough to move systems up to nine places on a leaderboard.

So every scored question has a line in the benchmark's `gold-audit.jsonl`:

```json
{"caseId": "...", "status": "accepted", "reviewer": "...", "reviewedAt": "2026-09-16"}
{"caseId": "...", "status": "disputed", "reason": "gold counts refunds as revenue", "reviewer": "...", "reviewedAt": "..."}
{"caseId": "...", "status": "corrected", "reason": "...", "evidenceSql": "select ...", "reviewer": "...", "reviewedAt": "...", "upstreamIssue": "https://..."}
```

- Accuracy is reported on **all** questions and on the **accepted** subset, always side by side.
- A correction never replaces the publisher's answer. Our reference is scored as an alternative beside it, and the disagreement is reported to the publisher.
- A question with no audit line stops the scorer.

## 5. Trust labels are scored

DQL labels every answer `certified`, `governed` or `review_required`, and can ask for clarification or decline. Reports show:

- **wrong answers labelled certified** as their own column. The target is zero; any other value is a product defect, reported as such;
- the full table of (right / wrong / declined / asked) × trust label;
- which path answered each question: a certified block, the semantic layer, or AI-written SQL, and whether a certified join was used.

When a benchmark includes questions the data cannot answer, a refusal counts as correct only when refusing was right.

## 6. Cost and latency

- Latency: median and 95th percentile per question.
- AI calls: mean and maximum per question, from DQL's run receipts.
- Cost: dollars per question at the provider's list price on the date in `pricing.json`. Cost is shown only when **every** question measured its token usage; otherwise the column reads "—". Cost is never estimated.

## 7. Matching answers

A question is correct when the rows Ask returned match the rows the benchmark's correct SQL returns on the same data. Column names and column order are ignored (a benchmark's `total_loss` and Ask's `sum_of_loss` are the same column), numbers compare within 1e-6, a date equals a midnight timestamp of the same day, and duplicate rows must appear the same number of times. When a question does not ask for an order, row order is ignored. The matcher is `lib/row-match.mjs`, with its own tests.

## 8. No tuning on the test set, and no path to the answers

- **DQL is not tuned to benchmark questions.** No prompt, code path or setting in DQL names a benchmark question, table or answer. DQL is run as released.
- **Layers are authored from documentation, not from answers.** Modeling (L1) and skills (L3) are written from the project's own documentation and the benchmark's published schema and ontology, without reading the questions or their correct SQL. No certified block is written for a benchmark question: that would be the answer itself.
- **Development questions are declared.** Any question whose answer or run is inspected while building the harness is listed in the benchmark's `dev-questions.json` with the reason, and its results are reported separately from the headline numbers.
- **The answers are not reachable.** The correct answers are stored in this repository, outside the DQL project Ask runs in. Ask queries only the project's warehouse.
- **Code is frozen before a scored run.** The report records the DQL version and commit, and a scored run from a modified or unreleased build is not published.

## 9. Before any number is trusted

- Every correct-answer query must run on our build of the data and its row counts must match the publisher's data files. If they do not, the build is wrong and nothing is published.
- Replaying the recordings on a clean machine must reproduce the published accuracy columns exactly.
